<domain>
## Phase Boundary

Align **OpenClaw versions and deploy lineage** across **local CLI/runtime**, **VPS Docker runtime** (via `openclaw-ops` only), and **Mac GUI gateway**, after the 02.1 simplification and 02.1.3 digest-snapshot patch pipeline. Deliver **explicit health gates** (`channels status --probe`, triage smoke, 02.1 regression checks), **pre/post snapshots**, **documented rollback checkpoints**, and verification that **02.1 retired surfaces stay gone** (no `OPENCLAW_TRIAGE_DRAFT_*`, no `openclaw-gws-triage-draft-agent`, no revival of the old auto-route draft loop).

This phase is **operations and verification**, not new product features.

<decisions>
## Implementation Decisions

### Target pinning (D-01 — D-03)

- **D-01:** Maintain a **single written target** in this phase’s planning artifacts: **npm/OpenClaw CLI semver line**, **upstream git SHA** (`~/openclaw-ops/vps/.openclaw-version`), and **patch set identity** (which files under `vps/patches/` apply). The VPS runtime is **upstream SHA + patches**, not “whatever was on npm last Tuesday.”
- **D-02:** **Local** `openclaw --version` MUST match the **documented target semver** for this rollout (same install channel the operator uses day-to-day — typically global npm matching the shipped release family).
- **D-03:** Record **post-deploy checksums** that matter for rollback: e.g. **`npm pack` tarball name/hash** after `build-patched-openclaw.sh`, and **`openclaw --version` inside the container** after `deploy.sh --with-core --restart`.

### Upgrade sequence and checkpoints (D-04 — D-06)

- **D-04:** **Order:** (1) **Local** — upgrade CLI, run `openclaw channels status --probe`; (2) **VPS** — `build-patched-openclaw.sh` → `deploy.sh --with-core --restart`, then `docker exec … openclaw channels status --probe`; (3) **Mac GUI** — upgrade/restart app so gateway runs on the **intended release family**, restart via normal app flow per `AGENTS.md`.
- **D-05:** **Checkpoint after each step:** capture `openclaw --version` (local + in-container), note **tarball** applied on VPS, and **Mac app version** from About/build — before proceeding to the next surface.
- **D-06:** **Rollback path:** Version-only rollback means **reinstall prior tarball** on VPS (pinned SHA + prior patch set), **revert local npm** to prior semver if needed, and **reinstall prior Mac app build** — documented as bullet steps in plan/UAT, not ad hoc.

### Smoke depth (D-07 — D-08)

- **D-07:** **Minimum smoke:** ROADMAP **UAT bullets** (manual triage digest sanity, inline tokens, `/bash tdr send-now <token>` on a test item, probes).
- **D-08:** Add a **short automated or copy-paste checklist** in verification docs: `grep`/runtime checks proving **no** `OPENCLAW_TRIAGE_DRAFT_*` in effective env, **no** `openclaw-gws-triage-draft-agent` on VPS `bin`, and **probe** success — so repeats are identical across operators.

### Mac GUI vs VPS coupling (D-09 — D-10)

- **D-09:** **Byte-identical npm package** between Mac GUI bundle and VPS container is **not required**. VPS may run **patched tarball** from `openclaw-ops`; Mac GUI tracks **Sparkle/stable app builds** that may lag patch-level churn.
- **D-10:** **Acceptance:** Same **target release family** (documented), gateway **starts cleanly**, **Telegram/triage critical path** matches ROADMAP UAT. If GUI lags behind VPS by one npm patch, record it explicitly in snapshots — **do not block** the phase on Sparkle cadence unless probes or triage regress.

### Claude's Discretion

- Exact wording of rollback RUNBOOK and where it lives (`openclaw-ops` README vs phase VERIFICATION only).
- Whether one shell script wraps grep-smoke or operators run documented one-liners.

</decisions>

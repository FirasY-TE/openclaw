# Phase 02.3: Triage inclusion — broaden inbox-of-today, exclude promotions/newsletters — Context

**Gathered:** 2026-05-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Expand triage **email inclusion rules** so the digest renders **everything received today except Spam**, sorted into **five tiers** — `Urgent / Needs reply / Needs attention / FYI / Newsletters & noise` — with **higher tiers = more rendering depth**, **fixed top-down order**, and a **Telegram-aware presentation** that keeps the first message ≤ 4096 chars and falls back to the file snapshot from Phase 02.1.3 when content exceeds the limit. Touchpoints: classifier in `gws-personal` / review scripts, promo/newsletter detection, digest rendering in `triage_digest_build.py`, and the **mandatory ops mirror** to `~/openclaw-ops/vps/scripts/**` before close.

**Out of scope (handled elsewhere):**

- Immediate (real-time) Urgent push outside the digest schedule → deferred to a follow-on phase.
- Inline-image / full-body fidelity tuning → Phase 02.4.
- Cross-thread grouping & table view → Phase 02.5.
- Beeper / Hospitable draft loops → Phases 3+.

</domain>

<decisions>
## Implementation Decisions

### Time window

- **D-01:** Keep the digest window as a **rolling 24-hour lookback** from run time (`LOOKBACK_HOURS = 24` in `scripts/deploy/lib/triage_digest_build.py`). **Revises Phase 2 D-01** (calendar-day CT) — deliberate update so the digest captures mail arriving **after** the 4:30 PM scheduled run on the next run, supporting an end-of-day inbox-zero pass.
- **D-02:** Header wording in the digest must honestly say **"past 24h"** (or equivalent), **not** "today" / "calendar day".

### Tier taxonomy

- **D-03:** The digest uses **five tiers** in this **fixed top-down order**:
  1. **Urgent**
  2. **Needs reply**
  3. **Needs attention**
  4. **FYI**
  5. **Newsletters & noise**
- **D-04:** **Spam is excluded entirely** (Gmail `SPAM`/`TRASH` labels are dropped — never listed in any tier).
- **D-05:** Every non-spam Gmail message in the 24h window **must land in exactly one tier**. The classifier may **never** return `None`/drop for a non-spam row — `FYI` is the explicit catch-all.

### Tier triggers

- **D-06: Urgent** — any of:
  - existing rules (`Priority=urgent`, `AlertNeeded=yes`, label `rental/urgent` or any `…/urgent`); **OR**
  - sender matches an **operator-tunable VIP allowlist** (addresses + domains, e.g. direct manager, key vendors); **OR**
  - subject matches an **operator-tunable urgent-keyword allowlist** (e.g. `urgent`, `asap`, `[ALERT]`, `outage`).
- **D-07: Needs reply** — any of:
  - existing rule (`DraftNeeded ∈ {yes, maybe}`); **OR**
  - user is in `To:` (not Cc:/Bcc:) **AND** sender is not in the **automation-sender allowlist**; **OR**
  - subject hints a question (`?`, `please confirm`, `re:` of a thread the user previously sent into, request patterns).
- **D-08: Needs attention** — any of:
  - existing rules (`CreateTask=yes` or `Priority ∈ {medium, high}`); **OR**
  - **calendar invites needing RSVP** (e.g. `.ics`/MIME `text/calendar` or invite-pattern subjects, status not yet `accepted`); **OR**
  - explicit-to-you mentions where the user is addressed but not reply-needed (e.g. on a small `To:` line with team CC).
- **D-09: FYI** — **catch-all** for non-spam mail that didn't match Urgent / Needs reply / Needs attention **and** didn't match the Newsletters & noise detector. Rendering depth depends on sender (D-13).
- **D-10: Newsletters & noise** — detection (operator-tunable):
  - **Trigger** (either): Gmail category `CATEGORY_PROMOTIONS` / `CATEGORY_UPDATES` / `CATEGORY_SOCIAL` / `CATEGORY_FORUMS` **OR** message has a `List-Unsubscribe` header (RFC 2369);
  - **Refinement:** an operator-tunable **automation-sender allowlist** can _promote_ a flagged sender to a higher tier (e.g. keep CASPR / Workday / JIRA digest pinned to FYI) and **demote** specific newsletter senders that escape detection.

### Tier precedence

- **D-11:** When multiple triggers match, **higher tier wins**. Precedence (top wins): `Urgent > Needs reply > Needs attention > FYI > Newsletters & noise`. A `List-Unsubscribe` header **never** beats a higher-tier match — important so a VIP newsletter still surfaces in Urgent if their domain is allowlisted.

### Rendering depth ("higher tier = more info")

- **D-12:** Render depth per tier:

  | Tier                    | Render shape                                                                                                    |
  | ----------------------- | --------------------------------------------------------------------------------------------------------------- |
  | **Urgent**              | summary line **+ token (if reply-eligible)** **+ `bodySummary`** **+ full-body blockquote** **+ finalize hint** |
  | **Needs reply**         | summary line + `bodySummary` + token + finalize hint + full-body blockquote (same as today for Gmail)           |
  | **Needs attention**     | summary line + `bodySummary` only (no full body)                                                                |
  | **FYI**                 | see D-13                                                                                                        |
  | **Newsletters & noise** | one-line per item, rendered inside a fenced code block (see D-15)                                               |

- **D-13: FYI render shape** depends on sender:
  - **Human sender** (not in the automation-sender allowlist) → `summary line + one-sentence bodySummary`.
  - **Automation sender** (in allowlist, but not noise-tier per D-10) → `summary line only` (sender + subject).

### Telegram presentation (the 4096-char reality)

- **D-14:** The **first Telegram message** must stay ≤ 4096 chars. Render priority — **Urgent + Needs reply + Needs attention always rendered in full**. **FYI and Newsletters & noise are truncated** as needed with a footer like:
  ```
  +N more in FYI · +M more in Newsletters & noise — see digest snapshot.
  ```
  The full digest is always written to `triage-digest-latest.md` and reaches the agent via the **Phase 02.1.3 `triageDigestSnapshot`** path (32 KB cap, no truncation in normal volumes).
- **D-15: Newsletters & noise** must render as a **fenced ` ``` ` code block** (Telegram does not render Markdown tables — pipes appear literally). Suggested per-line shape: `<sender> — <subject> — [<tag>]` where `<tag>` is `unsub` / `promo` / `social` / `automation`. Exact column ordering left to planner.
- **D-16: Per-tier caps** — current `CAP_PER_CATEGORY = 15` must be **rebalanced for five tiers**. **Planner picks the numbers** within the 4096-char budget. Constraints: Urgent/Needs-reply rarely exceed today's effective volume so they should not be the truncation source; FYI and Newsletters & noise should have explicit caps with `+N more` rollups; truncation is **always** safe because the file snapshot carries the full payload.

### Operator-tunable config

- **D-17:** Three operator-tunable lists are introduced:
  1. **VIP-sender allowlist** (addresses + domains) → promotes to Urgent.
  2. **Urgent-keyword allowlist** (subject regex/substring set) → promotes to Urgent.
  3. **Automation-sender allowlist** (addresses + domains) → demotes from Needs-reply / FYI to FYI-automation render shape and refines Newsletters & noise (D-10).

  Storage location, file format, and schema **left to planner** — must be operator-tunable without a code deploy (per the `prompts/triage-draft-runbook.md` pattern), and must be **mirrored** to `openclaw-ops/vps/scripts/**` per D-19.

### Ops mirror discipline

- **D-18: Source-of-truth mirror gate.** Every plan in this phase must:
  - mirror touched files from `openclaw/scripts/deploy/**` to `openclaw-ops/vps/scripts/**`;
  - deploy via `cd ~/openclaw-ops/vps && ./deploy.sh` and verify live behavior on the VPS;
  - assert byte-identity (`diff -q openclaw/scripts/deploy/<f> openclaw-ops/vps/scripts/<f>` returns empty) before close.
    This carries forward the 02.1.1 / 02.1.2 process lesson.
- **D-19:** New runtime config files (D-17 lists) must ship to `/data/openclaw-gws/config/` (or planner-chosen path) and be loaded by both `gws-personal` review and `triage_digest_build.py`.

### Classifier responsibilities

- **D-20:** `_categorize_gmail` in `scripts/deploy/lib/triage_digest_build.py` must be extended to:
  - read the three D-17 allowlists at load time;
  - return one of `urgent | needs_reply | needs_attention | fyi | newsletters_noise` (never `None` for non-spam);
  - apply precedence (D-11);
  - delegate noise-tier detection to a small helper that consumes Gmail category + `List-Unsubscribe` + automation-sender allowlist.
    Whether to extend the upstream `gws-personal` / `gws-rental` review scripts (so the input summary blocks already carry richer signals) or keep all logic inside `triage_digest_build.py` is **planner discretion** — both work; the review scripts already emit category labels and `BodyB64`.

### Claude's Discretion

- Exact file format / schema / on-disk path for the VIP, urgent-keyword, and automation-sender allowlists.
- Subject-pattern regex set for D-07 (question detection) and D-08 (RSVP detection).
- The keyword set seeded into the **urgent-keyword allowlist** (planner suggests; user reviews).
- Per-tier cap numbers (D-16).
- Truncation-footer wording (D-14).
- Whether classification widening happens upstream in `gws-personal` review or inside `triage_digest_build.py` (D-20).
- Internal JSON shape and any new fields on items.

</decisions>

<specifics>
## Specific Ideas

- **Apple-Tools precedent (`cursor_inbox_triage.md`)** — five-tier shape the user already validated in another product:
  - Urgent = VIP Tier 1 sender, single-row full detail.
  - Needs Attention = VIP Tier 2/3 + sprint/project mail, summary depth.
  - Calendar Invites surfaced as their own visible block (mapped here into Needs attention per D-08).
  - Newsletters & Automations rendered as a compact one-line-per-row table (mapped here to a fenced code block per Telegram constraint D-15).
- **Inbox-zero framing** — the digest is an _end-of-day pass toward zero_, not a "today's mail" board; rolling 24h (D-01) catches the long tail after 4:30 PM CT.
- **Tunable-without-deploy** — the runbook-markdown pattern (`prompts/triage-draft-runbook.md`) is a precedent: edit a tracked file, deploy reads it; no env-var soup, no patched core. The D-17 allowlists should follow the same shape.
- **Operator escape hatch** — when noise-tier detection misclassifies, the automation-sender allowlist (D-10 refinement, D-17 list 3) is the single tunable knob; no code changes needed.

</specifics>

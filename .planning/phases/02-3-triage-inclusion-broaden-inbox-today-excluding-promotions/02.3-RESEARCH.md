## Executive Summary

Phase 02.3 replaces the current "only surface `needs_reply`/`needs_attention`/`urgent`" classifier with a **five-tier catch-all classifier** that routes every non-spam message in the 24h window into exactly one bucket. The primary file to change is `scripts/deploy/lib/triage_digest_build.py` — specifically `_categorize_gmail` (add tiers + allowlist loading), `render_markdown` (add FYI and Newsletters render branches), and the top-level constants (`CAP_PER_CATEGORY` → per-tier caps). Three new plain-text config files land in `/data/openclaw-gws/config/` for operator-tunable VIP senders, urgent keywords, and automation senders. The review scripts (`openclaw-gws-review-test` / `openclaw-gws-review-rental-test`) need one new emitted field (`GmailCategory`) and pass-through of `List-Unsubscribe` presence (`HasListUnsubscribe: yes/no`) so the digest classifier can detect newsletters without re-fetching headers. Ops mirror discipline (D-18) applies to all touched files. The Phase 02.1.3 `triageDigestSnapshot` 32 KB safety net must be confirmed live before deploying 02.3 — Phase 02.3 will routinely produce >4096-char digests.

### Allowlist Loader

A new private function `_load_allowlists(base_dir: Path) -> dict` loads all three config files once at startup. Resides in `triage_digest_build.py` (same module; no separate file). This keeps blast radius contained to one module and avoids a new import dependency.

```python
def _load_allowlists(base_dir: Path) -> dict:
    config_dir = base_dir / "config"
    return {
        "vip_senders":        _load_sender_set(config_dir / "triage-vip-senders.txt"),
        "urgent_keywords":    _load_keyword_list(config_dir / "triage-urgent-keywords.txt"),
        "automation_senders": _load_sender_set(config_dir / "triage-automation-senders.txt"),
    }
```

### Five-Tier `_categorize_gmail`

```python
def _categorize_gmail(fields: dict[str, str], allowlists: dict) -> str:
    """Never returns None for non-spam rows (D-05). Precedence: D-11."""
    # 1. Spam exclusion (D-04) — caller responsibility via label check
    # 2. Urgent (D-06)
    if _is_urgent(fields, allowlists):
        return "urgent"
    # 3. Needs reply (D-07)
    if _is_needs_reply(fields, allowlists):
        return "needs_reply"
    # 4. Needs attention (D-08)
    if _is_needs_attention(fields):
        return "needs_attention"
    # 5. Newsletters & noise (D-10) — checked BEFORE FYI so D-11 is respected
    if _is_newsletter(fields, allowlists):
        return "newsletters_noise"
    # 6. FYI catch-all (D-09)
    return "fyi"
```

Spam exclusion (`SPAM`/`TRASH` in `Labels`) is checked in `build_items` before calling the classifier — this keeps the classifier pure and testable without label-parsing logic.

## Allowlist Schema Proposal

### Recommended Format: Plain `.txt` one-entry-per-line

**Files:**

```
/data/openclaw-gws/config/triage-vip-senders.txt
/data/openclaw-gws/config/triage-urgent-keywords.txt
/data/openclaw-gws/config/triage-automation-senders.txt
```

**Format (same as existing `family-vip-senders.txt` pattern in review scripts):**

```
# VIP senders — addresses or @domain patterns → promote to Urgent
# Lines beginning with # are comments. Blank lines ignored.
boss@company.com
@importantvendor.com
ceo@corp.net
```

```
# Urgent keywords — case-insensitive substring match against Subject
# One keyword/phrase per line. Prefix with / to use as regex.
urgent
asap
[ALERT]
outage
p0
p1
action required
```

```
# Automation senders — @domain or exact address
# These demote from Needs-reply to FYI-automation shape,
# and refine Newsletters & noise tier detection (D-10).
noreply@jira.example.com
@workday.com
@caspr.io
notifications@github.com
```

**Rationale:**

- Exact same loader pattern already in `openclaw-gws-review-test` (`load_sender_list`/`sender_matches`). Zero new concepts for operator.
- Operator edits a plain text file, runs `scp` or the `deploy.sh` to push — no JSON syntax errors, no schema validation friction.
- `#` comments make intent self-documenting.
- `@domain` prefix works for domain-level matching (same semantics as existing review scripts).
- For urgent-keyword list, bare strings are case-insensitive substring; `/regex` prefix allows regex for power users.

**Alternative: YAML/JSON single file**

```yaml
# triage-allowlists.yaml
vip_senders:
  - boss@company.com
  - "@importantvendor.com"
urgent_keywords:
  - urgent
  - asap
automation_senders:
  - "@workday.com"
```

Trade-off: single file simplifies deploy (one `scp`), but YAML requires PyYAML (not stdlib). JSON requires `json.load` (stdlib, fine) but is less operator-friendly (no comments, trailing commas error). The three-separate-`.txt` approach uses only stdlib `pathlib.Path.read_text` and follows the existing codebase pattern — **prefer `.txt`.**

**Deploy loop for operator:**

1. Edit `~/openclaw-ops/vps/scripts/config/triage-vip-senders.txt` locally.
2. `cd ~/openclaw-ops/vps && ./deploy.sh` (scp to VPS `/data/openclaw-gws/config/`).
3. No restart needed — `triage_digest_build.py` loads config on each run (cron).
4. Trigger a test run: `ssh openclaw-vps "docker exec openclaw-ridl-openclaw-1 bash /data/openclaw-gws/bin/openclaw-gws-triage-digest"` and inspect stdout.
5. `git commit && git push` once satisfied.

## Subject-Pattern Sets

### D-07 — Question / Reply-Needed Detection

These supplement the existing `DraftNeeded ∈ {yes, maybe}` check. Evaluated case-insensitively against the `Subject` field.

**Substring patterns (low false-positive):**

```python
QUESTION_SUBJECT_SIGNALS = [
    "?",                    # explicit question mark in subject
    "please confirm",       # action request
    "please advise",        # already in review scripts
    "let me know",          # already in review scripts
    "response required",    # already in review scripts
    "please reply",         # already in review scripts
    "can you",              # "can you review", "can you help"
    "could you",            # "could you send"
    "would you",            # "would you be available"
    "do you",               # "do you have a minute"
    "are you",              # "are you available"
    "following up",         # follow-up email
    "checking in",          # checking in
    "per our conversation", # professional follow-up
    "quick question",       # direct call-out
    "approval needed",      # workflow asks
    "your input",           # "need your input"
    "your feedback",        # "request your feedback"
    "your thoughts",        # "what are your thoughts"
]
```

**False-positive notes:**

- `"?"` — low risk in email subjects (rare cosmetic use); **do not** apply to `From:` field (newsletters sometimes use `?` in subject for click-bait → mitigated by D-11: newsletter detection runs after needs_reply; if already newsletter, won't re-fire). However if sender is in automation-sender allowlist, skip `?` signal.
- `"can you"` / `"could you"` — occasionally in automation subjects ("Can you review this autogenerated report?"). Mitigate: skip if sender in `automation_senders` allowlist.
- `"following up"` — low false-positive in personal Gmail; automation rarely uses this phrase.

**Implementation note:** Only apply these signals when `DraftNeeded` is not already `yes`/`maybe` (avoid double-triggering) AND sender is NOT in `automation_senders`. The existing review scripts handle `response_required_signals` there already; the D-07 check in `_categorize_gmail` is a second pass for signals the review scripts don't catch.

**D-07 also includes To: field check.** The review scripts currently emit `From:` but not `To:`/`Cc:`. For the "user is in `To:` (not Cc/Bcc)" check, the review scripts must also emit a `To:` field. If this field is absent, fall back to DraftNeeded signal only. The planner should decide whether to add `To:` emission to review scripts or defer To:-field check to a future phase.

### D-08 — RSVP / Calendar-Invite Detection

**Substring patterns:**

```python
CALENDAR_INVITE_SUBJECT_SIGNALS = [
    "invitation:",              # Gmail standard subject prefix for calendar invites
    ": invitation",             # variant
    "you're invited",
    "invited to",               # "you've been invited to"
    "join us for",
    "save the date",
    "please join",
    "rsvp",
    "rsvp by",
    "meeting request",
    "calendar invite",
    "event invite",
    "conference invite",
]

CALENDAR_INVITE_MIME_SIGNAL = "text/calendar"   # MIME type in message parts
ICS_ATTACHMENT_SIGNAL = ".ics"                  # attachment filename suffix
```

**Sender-based signals (high precision for Google Calendar):**

```python
CALENDAR_INVITE_SENDERS = [
    "calendar-notification@google.com",
    "invites-noreply@airbnb.com",
]
```

**False-positive notes:**

- `"invitation:"` — Gmail's calendar system prepends this exact prefix for all GCal invites. Very low false-positive.
- `"rsvp"` — rare in non-invite subjects but possible in newsletters. Mitigate: if sender is in `automation_senders`, skip RSVP detection (newsletters using "RSVP" are not calendar invites).
- `"please join"` — moderate false-positive risk in marketing email. Mitigate: only apply when NOT in newsletter tier and NOT in automation-sender allowlist.

**Implementation note:** For `.ics` / `text/calendar` MIME detection, the review scripts would need to inspect the message `payload.parts` to detect a MIME attachment. This requires additional logic in the review scripts. **Recommendation:** Start with subject-based signals only (no MIME inspection); add MIME detection as a follow-on. This keeps 02.3 blast radius small.

## Per-Tier Cap Math (D-16)

### Line-shape size estimates (Telegram UTF-8 chars, worst case)

| Tier             | Render shape per item                                                                                                   | Est. chars/item                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Urgent           | `- [personal] Subject — sender@domain\n  bodySummary (280 chars)\n  _Finalize…_\n\n> full body lines (≤4000 chars)\n\n` | ~4500 (with full body), ~400 (no body) |
| Needs reply      | Same as today: summary + bodySummary + token + finalize + blockquote                                                    | ~4500 / ~400                           |
| Needs attention  | `- [personal] Subject — sender\n  bodySummary (280 chars)\n`                                                            | ~400                                   |
| FYI (human)      | `- [personal] Subject — sender\n  One-sentence bodySummary (~120 chars)\n`                                              | ~280                                   |
| FYI (automation) | `- [personal] Subject — sender\n`                                                                                       | ~130                                   |
| Newsletters      | `  sender@domain — Subject (80 chars) — [unsub]\n` inside fenced block                                                  | ~130 per line                          |

**4096-char budget breakdown:**

| Component                                                     | Chars                                             |
| ------------------------------------------------------------- | ------------------------------------------------- |
| Header line (`**Triage digest** — window...`)                 | ~100                                              |
| `## Urgent` section header + affordance (rare)                | ~30                                               |
| Urgent items: cap = **3** (full body inline; most days = 0–1) | 3 × 4500 = 13500 (well over if all 3 have bodies) |
| `## Needs reply` section header                               | ~20                                               |
| Needs reply items: cap = **5** (with full body)               | 5 × 4500 = 22500 (way over)                       |
| ...                                                           |                                                   |

**Reality check:** Once Urgent and Needs-reply items are fully expanded, they can individually exhaust the 4096-char budget. The CONTEXT.md contract says "Urgent + Needs-reply + Needs-attention always rendered in full" — this means **the 4096 cap is structurally unenforceable for those three tiers** when content is large. The Phase 02.1.3 `triageDigestSnapshot` (32 KB file) is the authoritative delivery; the Telegram message is best-effort. For small volumes (≤2 urgent, ≤3 needs_reply, ≤5 needs_attention with short bodies), budget holds.

**Practical per-tier caps that fit ~4096 chars on average days:**

| Tier            | Recommended cap | Rationale                                                                                                                                       |
| --------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Urgent          | **5**           | Rare; full body inline; operator must see all. If overflow, snapshot covers it.                                                                 |
| Needs reply     | **5**           | ~400 chars/item (bodySummary, no full body in Telegram length calc since full body is from blockquote which can be long) — 5 × 400 = 2000 chars |
| Needs attention | **10**          | ~400 chars/item — 10 × 400 = 4000 chars (tight; safe with short bodySummaries)                                                                  |
| FYI             | **15**          | ~280 chars/item human, 130 automation — 15 × 200 avg = 3000 chars                                                                               |
| Newsletters     | **20**          | ~130 chars/line inside code block — 20 × 130 = 2600 chars                                                                                       |

**Combined worst-case (all tiers populated to cap):**

```
100 (header)
+ 5 × 400 (urgent, no-full-body mode)   = 2,000
+ 5 × 400 (needs_reply, no-full-body)   = 2,000
+ 10 × 400 (needs_attention)            = 4,000
+ 15 × 200 (fyi)                        = 3,000
+ 20 × 130 (newsletters code block)     = 2,600
+ ~200 (section headers, footers)
= ~13,900 chars
```

This exceeds 4096 well before FYI. **Key implication:** the 4096 budget invariant requires that Urgent + Needs-reply + Needs-attention combined stay under budget on typical days (they do: 0–2 urgent, 1–3 needs-reply, 2–5 needs-attention = ~300 + 1200 + 2000 = 3500 chars) and FYI/Newsletters are truncated first per D-14. The `+N more` footer is therefore structural, not exceptional.

**Revised approach:**

- Render tiers top-down; track running char count.
- After Urgent + Needs-reply + Needs-attention are emitted: compute remaining budget.
- Emit FYI items until budget exhausted; emit remainder as `+N more in FYI`.
- Emit Newsletter items until budget exhausted; emit remainder as `+M more in Newsletters & noise`.
- Always append the footer if anything was truncated.
- Full digest always written to file (no truncation there).

**Telegram MarkdownV2 overhead:** Special chars (`_*[]()~``>#+-=\|{}.!`) in sender names/subjects must be escaped → adds ~5–15% overhead for typical content. Per-item char estimates above already account for this roughly.

## Classifier Widening Locus (D-20)

### Recommendation: Keep widening inside `triage_digest_build.py`; add minimal new fields to review scripts only

**Rationale:**

1. **Blast radius.** `triage_digest_build.py` is the single mutation target. Changes to review scripts risk breaking existing `DraftNeeded`/`AlertNeeded` signal emission and require ops-mirror of two additional files (`openclaw-gws-review-test`, `openclaw-gws-review-rental-test`).

2. **What the review scripts already emit.** Looking at both review scripts:
   - Personal: `Labels` includes Gmail label IDs (e.g., `CATEGORY_PROMOTIONS`, `CATEGORY_SOCIAL`). These are **already present** in the `Labels:` field today.
   - Rental: Same — `Labels: {", ".join(data.get("labelIds", []))}`.
   - **Therefore `GmailCategory` signal is already available** in the `Labels` field — `triage_digest_build.py` just needs to check for `CATEGORY_PROMOTIONS` etc. in the `Labels` value. No review script change needed for category detection.

3. **Missing signal: `List-Unsubscribe` header.** This header is not currently emitted. Two options:
   - **Option A (recommended):** Add `HasListUnsubscribe: yes/no` emission to both review scripts (one new field, ~5 lines each). Simple, low risk.
   - **Option B:** Skip `List-Unsubscribe` header detection and rely only on Gmail category labels for newsletter detection. This works for Gmail-categorized newsletters but misses transactional list mail that Gmail doesn't tag.

   **Recommendation: Option A** — add `HasListUnsubscribe: yes/no` to both review scripts. This is the minimal review-script change (one field) that unlocks D-10's full detection capability. The field is safe to add: existing tests don't assert on the absence of this field.

4. **To: field for D-07.** Current review scripts do NOT emit `To:` header. The D-07 "user is in To: not Cc/Bcc" sub-trigger requires it. **Recommendation:** Also add `RecipientTo: {to_header}` to review scripts. Fall back to `DraftNeeded` signal if absent for backward compat.

**Summary of review script additions (minimal):**

- Add `HasListUnsubscribe: yes/no` to both personal + rental review scripts.
- Add `RecipientTo: {to_header}` to both personal + rental review scripts.
- Mirror both to `openclaw-ops` per D-18.

All other new classification logic (VIP matching, keyword matching, tier precedence, newsletter tag assembly) lives entirely in `triage_digest_build.py`.

## Pitfalls & Regressions

### 1. MarkdownV2 escaping inside fenced code blocks

**Issue:** Telegram's Bot API MarkdownV2 mode requires escaping special chars (`_*[]()~``>#+-=\|{}.!`) — but **inside a fenced code block (` ``` ` ), NO escaping is needed** (Telegram renders the block literally). However, the fenced code block delimiters themselves (the triple backticks) must appear on their own line and must themselves be properly placed.

**Current code:** `render_markdown` constructs Markdown strings that go through `openclaw message send --message "${MSG}"` in the bash wrapper. The existing body blockquote (`> ` lines) go through MarkdownV2 escaping somewhere in the openclaw sender. The Newsletters fenced code block must be rendered as literal ` ```\n...\n``` ` and must not have the inner content escaped by that layer.

**Action:** Verify with a live test that the fenced code block arrives un-mangled. If the openclaw sender escapes the backticks, we need to use the MarkdownV2 pre-entity form instead (`` `...` `` → `\`...\``). Check actual Telegram send behavior with a short test digest.

**Risk level:** MEDIUM — this is the most likely rendering pitfall in 02.3.

### 2. Backward compat for existing tests

The test `test_overflow_line_after_15_items` (line 51) asserts on the current cap-15 overflow line wording. After replacing `CAP_PER_CATEGORY = 15` with per-tier caps, this test must be updated to match the new per-tier cap for `needs_attention` (or whatever tier the test uses — currently `needs_attention`).

The test `test_urgent_wins_over_needs_reply` (line 42) calls `tdb._categorize_gmail(fields)` with no `allowlists` argument. After the signature change to `_categorize_gmail(fields, allowlists)`, this call will break. Fix: provide a default empty `allowlists` arg, or update test to pass empty dict.

All other existing tests should pass without modification since `urgent`/`needs_reply`/`needs_attention` category values are unchanged.

### 3. Rolling 24h overlap / dedup

`LOOKBACK_HOURS = 24` is already the code reality (line 26 of `triage_digest_build.py` — header comment says `24`; the actual constant is also `24`). No change needed. The cron runs daily; the 24h window may capture the same message on two consecutive runs if it arrived near the boundary. The existing dedup mechanism (Message ID hex in draft state) prevents duplicate **draft tokens** but does NOT prevent duplicate **digest renders**. This is acceptable — the operator sees the item twice at most, and it falls off naturally after 24h.

**If this becomes noisy:** A per-run dedup state file (set of rendered `gmailMessageId` values) under `/data/openclaw-gws/state/triage-seen-ids.json` can be added as a follow-on. Not required for 02.3.

### 4. Phase 02.1.3 snapshot — 32 KB cap math

The `triageDigestSnapshot` reads `triage-digest-latest.md` with a 32 KB cap. A five-tier digest with full content (caps as proposed: 5 urgent × 4.5 KB full body + 5 needs_reply + 10 needs_attention + 15 FYI + 20 newsletters) can reach:

```
5 × 4500 + 5 × 4500 + 10 × 400 + 15 × 280 + 20 × 130
= 22500 + 22500 + 4000 + 4200 + 2600
= 55,800 chars ≈ 55 KB
```

This exceeds the 32 KB snapshot cap on pathological days. In practice: 0–2 urgent/needs_reply items with bodies + short needs_attention/FYI/newsletters fits comfortably. **The 32 KB cap is not a blocker** for normal operation; truncation in the snapshot file is silent (agent reads partial digest). No action required for 02.3, but worth noting for the operator.

### 5. Operator allowlist edit without breaking deploy

**Risk:** An operator edits `triage-vip-senders.txt` locally in `openclaw-ops/vps/scripts/config/`, forgets to `scp` it to the VPS, and wonders why the VIP isn't surfacing.

**Mitigation:** Document the edit loop explicitly in the runbook (or in the file's comment header). The `deploy.sh` in `openclaw-ops/vps/` should include the `config/` directory in its `scp` targets. The planner should verify `deploy.sh` covers `/data/openclaw-gws/config/` as a target (or add it).

### 6. `NEEDS_ATTENTION_AFFORDANCE` — appears in both old Needs-attention and new render

The affordance line `_Reply in this topic with "draft <name>"...` currently appears at the top of `## Needs attention`. With five tiers, the affordance should still appear only under `## Needs attention` (verbs are about drafting needs_reply items). No change needed; confirm the affordance does NOT accidentally appear under FYI or Newsletters.

### 7. `build_draft_state` — urgent items with tokens (D-12)

D-12 says Urgent includes "token (if reply-eligible)". Currently `build_draft_state` only mints tokens for `needs_reply`. Extending to `urgent` means:

- Urgent items with `gmailMessageId` AND `source in (personal_gmail, rental_gmail)` get tokens.
- `render_markdown` for Urgent tier must include the token + finalize hint (same as Needs-reply today).
- Test: `test_run_build_keeps_token_state_without_button_payloads` will need a new fixture with an urgent Gmail item.

### 8. Telegram fenced code block — MarkdownV2 vs HTML mode

OpenClaw's Telegram sender may use HTML parse mode rather than MarkdownV2. In HTML mode, `<pre>...</pre>` is the monospace block; backtick fencing is NOT recognized. Verify which parse mode `openclaw message send` uses for digest delivery — if HTML mode, the Newsletters tier fenced code block must use `<pre>` instead of ` ``` `. Check `send_telegram_target_message` in `telegram-topic-routing.sh` and the openclaw Telegram send implementation.

**From code review of `telegram-topic-routing.sh`:** The script calls `openclaw message send --channel telegram --target "${target}" --message "${message}"`. The parse mode is determined by openclaw's Telegram channel implementation. Given the existing blockquote syntax (`> ` lines) works in current digests, the channel likely uses MarkdownV2. Confirm before implementing the Newsletter fenced block.

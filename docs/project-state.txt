📅 Morning Brief System

Status: operational with dual-account data (Mar 16 2026)

Flow:

Gmail Review Agents run (personal + rental)
Calendar events fetched (personal GWS + ICS sources — see below)
Tasks fetched
System composes morning context with derived intelligence
Rental Gmail summary merged into context (rental_maintenance, rental_guest, rental_financial, rental_urgent buckets)
Derived alerts include both personal + rental items
Focus candidates include rental urgent and guest items

Output:

/data/openclaw-gws/output/morning-brief-context-latest.json

Gmail data sources:
  /data/openclaw-gws/output/gmail-review-summary-latest.txt (personal)
  /data/openclaw-gws/output/gmail-review-rental-summary-latest.txt (rental)

Calendar data sources (inputs.calendar in context JSON):
  - personal-gws: gws-personal — personal Google Calendar.
  - work: ICS file on workspace — work calendar is not exposed via GWS; an ICS is supplied (e.g. /data/.openclaw/workspace/calendar/work.ics).
  - personal-ics: optional fallback ICS (e.g. /data/.openclaw/workspace/calendar/personal.ics).

Rental calendar note:
  gws-rental can list/query the rental account Calendar API for ops and scripts, but morning-brief-context-latest.json does not add a separate “rental-gws” calendar merge unless openclaw-morning-context is extended on the VPS. Rental operational signal in the brief is primarily from rental Gmail. Feeds subscribed on the personal calendar (e.g. property ICS) appear under personal-gws events.

Delivery: terminal (future: notification, voice assistant)

🔵 PLAN DELTA — Updated Architecture + Execution Strategy (March 2026)
Purpose

Document how the original OpenClaw + Google Workspace rollout plan was modified during real implementation.

The original design was architecturally correct.
However, execution sequencing and operational hardening were adjusted to reduce risk and stabilize the system.

✅ Major Changes from Original Plan
1. Execution Order Changed — Stabilize One Account First

Original plan:

Build full dual-account architecture immediately

Actual implementation:

Stabilized single-account runtime first, then added rental

2. Runtime Storage Path Changed — Persistence Requirement

New standard runtime root:

/data/openclaw-gws

Structure:

/data/openclaw-gws/bin
/data/openclaw-gws/config
/data/openclaw-gws/output

3. Headless Auth Flow Clarified

Proven flow:

Authenticate on Mac → Export authorized credentials → Copy to VPS → Wrapper points to file

4. Wrapper Strategy Simplified — Smaller Components First

Build small persistent scripts, refactor into larger wrappers later if needed.

5. Morning Brief / Agent Wiring Split from GWS Infrastructure

Infrastructure stabilization must precede orchestration logic.

✅ Architectural Principles That Remain Correct

Subagents should not be used as authentication isolation boundaries

Separate wrapper scripts must be used for separate Google accounts

Personal Google Tasks should remain the master task system

Rental calendar should remain read-only

Draft-first email workflows are safer than auto-send

Heartbeat / cron automation should be added only after manual validation

Rental path uses direct account auth, not delegated Gmail API access
